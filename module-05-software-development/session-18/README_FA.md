# جلسه ۱۸: مدیریت خطا و اشکال‌زدایی

## مرور جلسه

تا اینجا همه‌چیز فرض می‌کرد برنامه‌تان ورودی معقولی می‌گیرد. برنامه‌های واقعی این‌طور نیستند. این جلسه خطا را به‌جای شکست، اطلاعات بازتعریف می‌کند: سه دسته خطا یعنی چه، چطور یک traceback را بخوانیم، چطور خطاهای مورد انتظار را با `try/except` بگیریم در حالی که خطاهای غیرمنتظره را عمداً به‌شدت ببندیم تا فریاد بزنند، و چطور به‌جای حدس زدن، سیستماتیک اشکال‌زدایی کنیم.

## اهداف یادگیری کلیدی

در پایان این جلسه می‌توانید:

- **تفکیک کنید** خطاهای نحوی، زمان اجرا و منطقی
- **بخوانید** یک traceback را از پایین به بالا و خط واقعی خرابی را پیدا کنید
- **مدیریت کنید** خرابی‌های مورد انتظار را با `try/except/else/finally`
- **انتخاب کنید** کدام استثناها را بگیرید و کدام‌ها را بگذارید بالا بروند
- **اشکال‌زدایی کنید** با print، assertion، logging و `pdb`
- **تشخیص دهید** خطای منطقی سخت‌ترین نوع است، چون هیچ‌چیز شکایت نمی‌کند

## سه نوع خطا

```
    SYNTAX ERROR       Python cannot parse the code at all.
                       Nothing runs. Usually a missing colon,
                       unbalanced bracket, or typo.

    RUNTIME ERROR     The code parsed, started, and then failed.
                       Python stops and shows a traceback.

    LOGIC ERROR        The code ran perfectly and produced
                       the wrong answer. Nothing complains.
                       This is the dangerous one.
```

دسته سوم دلیل آن است که تست مهم است. برنامه‌ای که کرش می‌کند دارد چیزی به شما می‌گوید. برنامه‌ای که بی‌سروصدا میانگین غلط را حساب می‌کند چیزی نمی‌گوید.

## خواندن traceback

traceback ها **از پایین به بالا** خوانده می‌شوند. آخرین خط خطاست؛ خط‌های بالاتر زنجیره فراخوانی‌ای را نشان می‌دهند که به آن رسیده.

```
Traceback (most recent call last):
  File "grades.py", line 42, in <module>
    report = generate_report(students)
  File "grades.py", line 58, in generate_report
    average = sum(scores) / len(scores)
ZeroDivisionError: division by zero
```

این‌طور بخوانید: برنامه در خط ۴۲ شروع شد، `generate_report` را صدا زد، و آن در خط ۵۸ موقع تقسیم بر صفر مرد. جایی که باید نگاه کنید خط ۵۸ است، نه خط ۴۲.

## try/except و محدودیت‌هایش

```python
try:
    age = int(input("How old are you? "))
except ValueError:
    print("Please enter a number.")
```

شکل کامل چهار بخش دارد:

```python
try:
    result = risky_operation()
except ValueError as e:
    print(f"Bad value: {e}")
except KeyError:
    print("Missing key")
else:
    print("No error - this only runs on success")
finally:
    cleanup()          # در هر صورت اجرا می‌شود
```

دو قاعده که این را از بوی بد کد دور نگه می‌دارد:

۱. **استثنای مشخص بگیرید، نه `except:` خام.** `except` خالا غلط‌های تایپی خودتان را هم می‌بلعد و یک عصر وقت‌تان صرف این می‌شود که چرا یک متغیر `None` است.
۲. **از `try` برای پنهان کردن باگ استفاده نکنید.** برای خرابی‌هایی که واقعاً انتظارشان را دارید، مثل ورودی کاربر یا فایل گم‌شده. یک `TypeError` که از باگ منطقی خودتان آمده باید کرش کند تا متوجهش شوید.

## تکنیک‌های اشکال‌زدایی

به ترتیب مفید بودن:

```
    1. READ THE ERROR MESSAGE   It usually names the problem exactly.

    2. REPRODUCE IT             Find the smallest input that fails.
       Every time, the same way.

    3. BISECT                   Comment out half the code.
       Which half still fails?

    4. PRINT THE STATE          print(repr(x)) not print(x).
       repr() shows quotes, so an
       empty string is visible.

    5. ASSERT                   assert 0 <= score <= 100, "score out of range"
       Fires at the moment the
       assumption breaks.

    6. pdb                      python -m pdb broken.py
       Step line by line, inspect
       variables, continue.

    7. RUBBER DUCK              Explain it out loud, line by line,
       to an object that cannot
       help. You will find the bug
       mid-sentence.
```

## مفاهیم اصلی

- **نحوی، زمان اجرا، منطقی**: سه دسته با سه راه‌حل متفاوت
- **traceback از پایین به بالا خوانده می‌شود**؛ آخرین خط خطاست
- **`try/except/else/finally`**: `else` در موفقیت، `finally` همیشه
- **استثنای مشخص بگیرید**؛ `except` خالا باگ‌های خودتان را پنهان می‌کند
- **از `try` برای پنهان کردن خطای منطقی استفاده نکنید**؛ بگذارید کرش کند
- **`repr()`** مشکلات نامرئی مثل رشته خالی را آشکار می‌کند
- **`assert`** یک فرض را مستند و بررسی می‌کند
- **`pdb`** گام‌به‌گام روی اجرای واقعی حرکت می‌کند

## اشتباهات رایج مبتدی

| اشتباه | پیامد |
|--------|--------|
| `except` خام | غلط‌های تایپی، `NameError` و هر چیز دیگری را می‌بلعد. برنامه بی‌صدا بد رفتار می‌کند |
| گرفتن استثنا و چاپ نکردن هیچ‌چیز | خرابی نامرئی می‌شود و بعداً دوباره سراغ می‌آید |
| `print(x)` برای دیباگ یک رشته خالی | انگار چیزی چاپ نشده. از `print(repr(x))` استفاده کنید |
| خواندن فقط اولین خط traceback | آن *علت* است نه *محل*. به بالا بخوانید |
| پیچیدن کل برنامه در `try/except` | هر باگ می‌شود «یک اتفاقی افتاد» |
| فرض اینکه نبود خطا یعنی درستی | خطاهای منطقی اصلاً خطا تولید نمی‌کنند |

## فعالیت‌های کارگاه

۱. **رفع کد.** پنج قطعه‌کد خراب. باگ‌ها را پیدا کنید، بگویید هرکدام از کدام سه دسته است، بعد درستشان کنید.
۲. **ورودی مقاوم.** برنامه ورودی جلسه ۱۲ را بردارید و طوری تغییر دهید که تا گرفتن یک عدد صحیح معتبر با حلقه `while` و `try/except` دوباره بپرسد.
۳. **تمرین traceback.** سه traceback. برای هرکدام نام فایل، شماره خط، نوع استثنا و کاری که برنامه می‌خواست بکند بنویسید.
۴. **پیدا کردن خطای منطقی.** برنامه‌ای که بدون کرش اجرا می‌شود ولی میانگین غلط برمی‌گرداند. با `print(repr(...))` دلیلش را پیدا کنید.

## تکالیف

- **کارهای دیباگ**: پنج قطعه‌کد کوتاه با باگ. برای هرکدام دسته خطا را نام ببرید، علت را توضیح دهید و راه‌حل را بنویسید.
- **گزارش خطا**: هنگام انجام بقیه تکالیف، هر پیام خطایی که دیدید و روش رفعش را ثبت کنید. این می‌شود مرجع شخصی شما.
- **تبدیل امن**: تابعی به نام `read_number(prompt)` بنویسید که تا گرفتن یک عدد معتبر بپرسد و بعد آن را برگرداند. از آن در یک برنامه کوچک استفاده کنید.
- **پیش‌بینی**: با توجه به سه بلوک `try/except`، دقیقاً بنویسید برای ورودی‌هایی که استثنا می‌دهند، استثنا نمی‌دهند، و استثنای مدیریت‌نشده می‌دهند چه اتفاقی می‌افتد.

## نکات کلیدی

- خطای نحوی قبل از اجرا متوقف‌تان می‌کند. خطای زمان اجرا حین اجرا. خطای منطقی اصلاً متوقف‌تان نمی‌کند.
- traceback از پایین به بالا خوانده می‌شود؛ پایین‌ترین خط جایی است که باید نگاه کنید.
- استثنای مشخص بگیرید. `except` خالا تله است.
- از `try/except` برای خرابی‌های مورد انتظار استفاده کنید، نه برای پنهان کردن باگ.
- `repr()` و `assert` چیزی را می‌گیرند که `print` نمی‌گیرد.
