# جلسه ۶: نمایش متن، ASCII و یونیکد

## مرور جلسه

کامپیوتر نمی‌تواند حرف `A` را ذخیره کند. فقط می‌تواند عدد ذخیره کند. جایی میان حرفی که تایپ می‌کنید و بیت‌های روی دیسک، یک سیستم کدگذاری تصمیم می‌گیرد که کدام عدد یعنی `A`. این جلسه آن گام را آشکار می‌کند، نشان می‌دهد چرا سیستم ۷ بیتی ASCII که انگلیسی به‌راحتی در آن جا می‌شود نمی‌تواند جمله فارسی یا چینی را نگه دارد، و یونیکد و UTF-8 را به‌عنوان پاسخ معرفی می‌کند. این نخستین جلسه‌ای است که یک باگ کدگذاری واقعی می‌تواند داده شما را برای همیشه خراب کند، پس می‌بینیم وقتی کدگذاری اشتباه فرض شود چه اتفاقی می‌افتد.

## اهداف یادگیری کلیدی

در پایان این جلسه می‌توانید:

- **توضیح دهید** که کاراکترها به شکل عدد ذخیره می‌شوند، نه به شکل شکل ظاهری حرف
- **تفاوت بگذارید** بین ASCII و یونیکد
- **توصیف کنید** چرا یونیکد لازم شد و چه مسئله‌ای را حل کرد
- **تشخیص دهید** UTF-8 و UTF-16 را از روی الگوی بایت‌هایشان
- **شناسایی کنید** mojibake و بگویید چه چیزی باعثش شده
- **تبدیل کنید** یک رشته کوتاه را با دست به بایت و دوباره برگردانید

## کاراکترها عدد هستند

حرف `A` روی صفحه‌کلید شما فقط یک کلید است. با فشردن آن، سیستم‌عامل با استفاده از یک جدول agreed، چیزی تولید می‌کند که به عدد تبدیل می‌شود:

```
    آنچه تایپ می‌کنید         آنچه کامپیوتر ذخیره می‌کند        آنچه برمی‌گردد

        A                       65  (0b01000001)                  A
        B                       66  (0b01000010)                  B
        a                       97  (0b01100001)                  a
        b                       98  (0b01100010)                  b
        0                       48  (0b00110000)                  0
        1                       49  (0b00110001)                  1
```

به پرش عددها دقت کنید. `a` برابر ۹۷ است ولی `A` برابر ۶۵. فاصله ۳۲ عددی دقیقاً تفاوت حروف بزرگ و کوچک است و تصادفی نیست.

## چرا ۷ بیت کافی نبود

ASCII هفت بیت را تخصیص می‌دهد که ۱۲۸ نقطه کد را پوشش می‌دهد:

```
    7 bits = 128 possible values
    ASCII uses them for:
      0-31    control characters (newline, tab, backspace)
      32-126  printable English: space, digits, punctuation, A-Z, a-z
      127     delete

    That is the entire ASCII world. English, plus punctuation.
```

حالا به یک جمله فارسی یا چینی فکر کنید. هرکدام از این زبان‌ها هزاران کاراکتر دارند. سه پیامد از این نتیجه می‌شود:

۱. یک بایت برای هر کاراکتر کار نمی‌کند.
۲. زبان‌ها باید فضای عددی را به اشتراک بگذارند بدون برخورد.
۳. یک بایت نمی‌تواند اعلام کند کاراکتر بعدی چند بایت طول می‌کشد.

## یونیکد مسئله فضای عددی را حل می‌کند

یونیکد به هر کاراکتر در هر زبان نوشته‌شده یک عدد یکتا به نام **نقطه کد** می‌دهد:

```
    'A'    U+0041        Persian 'ا'    U+0627
    'a'    U+0061        Persian 'ب'    U+0628
    '0'    U+0030        Chinese '中'   U+4E2D
    '€'    U+20AC        Emoji '🎉'      U+1F389
```

پیشوند `U+` و چهار رقم شانزده‌شانزدهی، همان نشانه‌گذاری است. خود یونیکد *اعداد* را تعریف می‌کند. اینکه آن اعداد چگونه به بایت تبدیل شوند کار کدگذاری‌های UTF است و بیشتر سردرگمی واقعی دقیقاً همین‌جاست.

## یونیکد در برابر UTF-8: دو چیز متفاوت

```
    Unicode          = the code point table      (a dictionary)
    UTF-8            = one encoding of that table (a spelling)

    '€' has code point U+20AC.

    Encoded as UTF-8:    E2 82 AC        (3 bytes)
    Encoded as UTF-16:   20 AC           (2 bytes)
    Encoded as UTF-32:   00 00 20 AC     (4 bytes)

    Same character. Different bytes. Same meaning.
```

UTF-8 پیش‌فرض عملی است: برای ASCII یک بایت می‌گیرد، پس داده‌های انگلیسی موجود تغییری نمی‌کنند، و فقط برای کاراکترهای غیر ASCII بزرگ می‌شود.

## mojibake: علامتی که باید بشناسید

این را دیده‌اید. `café` تبدیل می‌شود به `cafÃ©`. دقیقاً چه اتفاقی افتاد:

```
    The original text            café
    Encoded as UTF-8             63 61 66 C3 A9
    Decoded as Latin-1 (wrong)   c a f Ã ©
```

دو بایت (`C3 A9`) هرکدام به‌عنوان یک کاراکتر جداگانه Latin-1 خوانده شدند. چیزی گم نشد؛ بایت‌ها سالم‌اند. ولی خواننده دیگر نمی‌تواند بفهمد منظور UTF-8 بوده یا Latin-1. این همان باگ کدگذاری است که دست‌کم یک بار در حرفه‌تان دیباگ می‌کنید.

## مفاهیم اصلی

- **نقطه کد**: عددی که یونیکد به یک کاراکتر می‌دهد
- **ASCII**: استاندارد ۷ بیتی با ۱۲۸ مقدار برای انگلیسی
- **یونیکد**: فضای عددی مشترک برای همه زبان‌های نوشته‌شده
- **UTF-8، UTF-16، UTF-32**: کدگذاری‌های آن فضا با عرض بایت متفاوت
- **عرض متغیر**: UTF-8 بسته به نقطه کد از ۱ تا ۴ بایت می‌گیرد
- **mojibake**: متنی که با کدگذاری اشتباه رمزگشایی شده
- **BOM**: نشانگر اختیاری ابتدای فایل که امروز برای UTF-8 توصیه نمی‌شود

## فعالیت‌های کارگاه

۱. **رمزگشایی با دست.** کدهای ASCII `72 101 108 108 111` به شما داده می‌شود. حروف را بنویسید. بعد با `print(bytes([72, 101, 108, 108, 111]).decode("ascii"))` بررسی کنید.
۲. **نام شما در نقاط کد.** نقطه کد هر کاراکتر از نام خودتان را با `ord()` پیدا کنید و ثبت کنید. دقت کنید یک نام نسبت به تعداد حروفی که به نظر می‌رسد چند نقطه کد می‌گیرد.
۳. **رفت‌وبرگشت یک جمله فارسی.** در پایتون یک جمله فارسی بگیرید، `.encode("utf-8")` را صدا بزنید، بایت‌ها را چاپ کنید، بعد با `.decode("utf-8")` برگردانید. همین کار را با `.encode("ascii")` تکرار کنید و خطا را با دقت بخوانید.
۴. **عمداً خرابش کنید.** متن را به‌صورت UTF-8 کدگذاری کنید، به Latin-1 رمزگشایی کنید، بعد به cp1256. خسارت را مقایسه کنید. کدام بازیابی‌پذیر است؟

## تکالیف

- **پاسخ‌های کوتاه**: چرا ASCII کافی نیست؟ یونیکد چه مسئله‌ای را حل می‌کند که ASCII نتوانست؟
- **یافتن کد**: نقطه کد پنج ایموجی را پیدا کنید و همراه دنباله بایت UTF-8 آن‌ها ثبت کنید.
- **بررسی کدگذاری**: یک فایل واقعی روی کامپیوترتان که UTF-8 نیست پیدا کنید، یا برنامه‌ای بنویسید که عمداً mojibake تولید کند و توضیح دهید چه اشتباهی رخ داد.
- **تأمل**: یک تا دو بند درباره اینکه چرا استاندارد کدگذاری بیش از آنچه به نظر می‌رسد اهمیت دارد.

## نکات کلیدی

- کامپیوتر عدد ذخیره می‌کند. جدول‌های کدگذاری عدد را به کاراکتر نگاشت می‌کنند.
- ASCII صد و بیست و هشت مقدار دارد و انگلیسی تقریباً همه‌شان را مصرف می‌کند.
- یونیکد فضای عددی مشترک است، نه قالب بایت.
- UTF-8 کدگذاری است. در بیشتر اوقات و در همه جا همان را می‌خواهید.
- mojibake اشتباه در رمزگشایی است نه از دست رفتن داده، و به‌محض شناختن الگو تشخیصش آسان است.
